# nanobot 自动化测试策略

## 1. 项目目标

本仓库从使用者视角验证 nanobot 的公开 HTTP API 和 WebUI。它不复制上游仓库的单元测试，也不以用例数量为目标，而是展示一套可以独立安装、稳定执行、持续集成和定位失败的测试工程。

首版范围：

- API：OpenAI 兼容接口的可用性、鉴权、请求校验、普通响应和 SSE 流式协议。
- UI：用户可见的关键链路、浏览器交互和少量高价值回归场景。
- 暂缓：真实模型效果评测、多浏览器兼容、移动端、性能和长稳测试。

## 2. 为什么 XMind 不能直接逐条变成 UI 脚本

XMind 描述的是 WebUI 功能，并不等于每条都应该经过浏览器验证。浏览器测试运行慢、定位器容易受界面变化影响，适合验证“用户是否真的能完成操作”；大量输入校验和协议边界更适合放在 API 或上游单元测试层。

采用以下分层原则：

| 层级 | 适合验证 | 本项目做法 |
| --- | --- | --- |
| API 黑盒 | 鉴权、状态码、字段约束、SSE、附件协议 | 使用真实 nanobot API 进程和本地 Mock 模型 |
| UI E2E | 键盘、拖拽、弹窗、视觉状态、完整用户路径 | Chromium + Page Object，只保留关键路径 |
| 混合场景 | 会话、自动任务、设置等需要复杂前置数据的页面 | 用 API/fixture 造数，再由 UI 验证展示与操作 |
| 上游单元/组件 | 纯函数、React 组件细节、内部异常分支 | 不在独立黑盒仓库重复 |

## 3. 风险优先级

优先自动化以下风险：

1. 服务无法启动，API 或 WebUI 不可访问。
2. 聊天请求无法完成，流式响应不符合协议。
3. 未授权请求可以访问受保护接口。
4. 输入、附件或会话状态在前后端之间丢失。
5. 已经发现且可以稳定复现的产品缺陷。

低优先级场景（排序样式、低频设置、依赖重启或网络中断的流程）等核心回归稳定后再加入。

## 4. 测试数据和环境

- 每次 pytest 会话创建临时配置和临时 workspace，不修改用户配置。
- 模型调用指向本地 Mock，避免密钥、费用和不确定回复。
- API、Gateway 和 Mock 都由 fixture 启停，失败日志复制到 `reports/logs/` 并附加到 Allure。
- 动态业务数据使用唯一后缀，避免重复执行时互相污染。
- 超时、上游异常、慢速流和断流由 Mock 控制标记确定性触发，不依赖真实网络故障。
- 会话并发使用独立 HTTP Client，避免共享 `requests.Session` 引入伪并发问题。
- 已确认的产品缺陷使用严格 `xfail`；环境问题和脚本问题不能登记为产品缺陷。

## 5. 自动化准入规则

一条用例进入主回归集前必须满足：

- 断言对应用户可观察结果或公开协议，而不是内部实现。
- 可以独立重复执行，不依赖个人账号和既有本地数据。
- 失败时有足够证据：Allure 分层与标签、服务日志、失败截图、HTML 报告和 Playwright trace。
- 没有固定等待；使用状态轮询或 Playwright 自动等待。
- 测试名称能说明行为和预期结果。

## 6. 后续性能测试入口

功能回归稳定后再建立 `tests/performance/`。第一批指标建议为 `/v1/chat/completions` 的成功率、并发吞吐、P95 响应时间和流式首包时间。性能基线必须固定 nanobot 版本、Mock 延迟、并发模型和运行机器，不能与功能测试共用“通过/失败”标准。
